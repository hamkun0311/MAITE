# 알림 조회·인증 비용 개선

## 요청 흐름

기존에는 CheckinInbox와 PushBridge가 각자 60초 타이머로 inbox와 schedule을 조회했다. 두 GET은 각각 requireAccount/getUser로 Auth 서버에 접근했다. 새 클라이언트는 PushBridge의 단일 타이머에서 `/api/notifications?sync=1`을 호출하고 읽지 않은 안부·알림 설정·캐릭터 활동·최근 발송 기록을 함께 받는다. 네 DB 조회는 병렬 처리하며 Server-Timing의 auth/inbox_db/preferences_db/activity_db/last_checkin_db/schedule_db를 유지한다. DB 조회 자체를 없앤 변경은 아니다.

CheckinInbox는 공유 결과를 구독하며 별도 요청·타이머를 두지 않는다. 읽지 않은 수가 같으면 상태 객체를 유지한다. 공유 조회는 10초간 결과를 재사용하고 진행 중인 호출을 합친다. 변경 중인 응답은 게시하지 않고 한 번 더 읽어 최신 상태를 반영한다. 계정 전환/로그아웃 시 공유 상태를 비우고 이전 계정의 응답을 게시하지 않는다. 안부 문구에는 최신 계정 프로필의 닉네임을 우선해, 서명 토큰에 저장된 이전 닉네임으로 되돌아가지 않도록 한다. 이 닉네임은 문구용이며 권한 판단에는 사용하지 않는다.

예약 동기화도 동일 계정/세대의 진행 중인 작업을 공유한다. 포커스/복귀 이벤트는 150ms로 묶고, 설정·저장·읽음·안부 도착 이벤트는 공유 데이터를 무효화한다. 숨겨진 화면에서는 정기 조회를 건너뛰고 복귀 시 재확인한다. 이미 예약된 안부의 마감 타이머와 Android 로컬 알림은 유지한다. 상태 안내가 같으면 저장/이벤트를 반복하지 않는다. 기존 캐릭터별 하루 1회·답장 전 재발송 금지·야간 제한·3분 테스트 대기 시간은 유지한다.

## 인증

통합 조회만 requireNotificationAccount를 사용한다. SDK getClaims로 JWT 서명·만료를 검증하고 발급자(현재 프로젝트 auth/v1)·audience·authenticated 역할·사용자 UUID·nbf를 추가 확인한다. 단순 JWT 디코딩이나 클라이언트가 보낸 사용자 ID는 신뢰하지 않는다. 비대칭 키는 캐시한 JWKS로 검증하며 기존 HS 키는 SDK가 원격 getUser로 검증한다. 공개 JWKS 읽기 전용 확인에서 현재 연결 프로젝트는 ES256 키를 제공했다. 이미 발급된 토큰의 알고리즘이 바뀌었다고 가정하지 않는다.

검증에 성공한 동일 토큰의 읽기 신원은 최대 30초, 토큰 만료 시각 이내로 재사용한다. 토큰은 원문 대신 발급자+토큰의 SHA-256 키로 구분하며 최대 500건을 보관한다. 진행 중인 검증은 합치고 실패는 캐시하지 않는다. 인증 토큰이나 원문을 로그하지 않는다. 로컬 검증은 최신 Auth 사용자 상태를 매 조회마다 원격 조회하는 방식과 같지 않다. 설정 변경·읽음·발송 기록의 POST, 하트·결제·기타 API의 기존 원격 확인은 유지한다. 사용자별 DB 필터·소유권/삭제 여부 검사·no-store도 유지한다.

이전 앱 호환을 위해 기존 inbox/schedule/document/설정 GET과 POST 계약은 유지한다. 대화 화면의 개별 캐릭터 메시지 조회는 기존 경로로 남는다. 새 통합 조회의 원격 인증 감소를 모든 API에 적용했다고 설명하지 않는다. DB 마이그레이션·인증 키 회전·추가 유료 서비스 설정은 필요 없다.

## 검증

실제 테스트 키로 ES256 JWT를 서명해 SDK의 검증 경로를 실행한다. 잘못된 서명·발급자·역할·audience·사용자 ID·만료·무인증은 거절한다. HS 원격 fallback/검증 중복 제거/실패 미캐시/만료 상한, 병렬 DB 조회와 삭제·타 계정 필터, 클라이언트 중복 요청/변경 중 재조회/계정 격리를 검사한다. 브라우저에서는 주기당 통합 요청 1회·별도 inbox/schedule 0회·복귀 이벤트 묶음·읽음 배지·캐릭터별 3분 안부를 확인한다. 테스트 대역 기반 검증이며 실서비스 프레임 지연이나 응답 개선 배율을 측정한 결과는 아니다.
